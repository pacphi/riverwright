## Context

The core spec §3.1 made the repository root both the plugin root and the marketplace. The owner asked whether a
`plugin/` subfolder is closer to standard practice, because users will balk at anything that interferes with their
own established configuration. The evidence is in [the layout research](../research/plugin-layout.md):

- An install adds an entry to a settings file for the scope the user chooses and fills its own cache; nothing was
  found that writes a user's `CLAUDE.md`. The concern is what else travels with the plugin.
- A git marketplace is cloned whole, but only the plugin directory is copied into the cache, and files outside it
  are not copied. A root plugin therefore ships the whole repository (docs, plans, tests, contributor rules) to every
  user, and two public cases show the cost: long paths broke Windows installs, and an install scanner flagged
  documentation that mentions `AGENTS.md`.
- Six of the code repositories surveyed that ship a CLI keep the plugin in a subfolder, and the official marketplace
  lists such plugins by `git-subdir`. Two large projects ship from the root, so both layouts work.
- A root `GEMINI.md` reaches Gemini users as extension context, and Gemini needs its manifest at the repository root.
- Subfolder plugins reach their CLI through a separate install. Riverwright cannot, because its hooks must fail
  closed when Node is missing, so its launcher must travel with the plugin.

## Decision

We will ship the plugin from a generated `plugin/` folder and make the repository root only the marketplace.

1. `.claude-plugin/marketplace.json` sits at the repository root and lists the plugin with `source: "./plugin"`.
   There is no `plugin.json` at the root.
2. `plugin/` is generated by `tools/generate-adapters.mjs` from the sources that stay at the root (`bin/`, `scripts/`,
   `templates/`, `skills/`, `roles/`, `references/`, `adapter-src/`), and it holds the plugin's own
   `.claude-plugin/plugin.json`, hooks, agents and commands. It is committed, because a git marketplace installs from
   what is in git.
3. `node tools/generate-adapters.mjs --check` fails when `plugin/` differs from what the generator would write or
   contains an orphaned file. CI runs it. `plugin/` is marked generated and is excluded from Markdown lint.
4. Contributor material (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `docs/`, `tests/`, `tools/`, `adapter-src/`) is never
   copied into `plugin/`. The root `CLAUDE.md` stays where it is.
5. `plugin/` contains real files, not symlinks. Windows checkouts without symlink support would break, and
   dereferencing on a real install is untested.
6. The plugin's hooks carry `--home account` ([core spec §7.2](../specs/core-single-issue-pipeline.md)), because one
   committed file serves every user.

We rejected: keeping the plugin at the root with the `CLAUDE.md` move (it ships the whole repository and does not
address the Gemini leak); moving the runtime into `plugin/` as its only copy (a rewrite of every path in the tests,
CI and three plans); and symlinks from `plugin/` to the root sources (see point 5).

## Consequences

**Positive:** users receive only what the plugin runs; contributor rules and documentation never reach a user's
cache; strict validation passes for both the marketplace and the plugin manifest without moving `CLAUDE.md`; tests
and Plans 2a and 2b keep their paths; the layout matches the closest public precedent for a repository that ships a
CLI.

**Negative:** generated files are committed twice, so pull requests show duplicates and a contributor could edit the
copy (the drift check catches it); the generator does more; a Gemini extension, when built, still needs a root
manifest and a `contextFileName` that keeps the root `GEMINI.md` out of users' context.

**Neutral:** Codex, Cursor and Grok read `.claude-plugin/` and see the same marketplace.

## Verification

`claude plugin validate --strict .` and `claude plugin validate --strict ./plugin` both pass (reproduced on a
throwaway copy of this layout). The drift check is clean in CI. A test asserts that `plugin/` contains no contributor
file and no symlink. The local-marketplace install is an owner step.
